# Internals

Detail moved out of the README: how the archive, impact levels, pages and EU critical-medicine matching work. Nothing was changed except the title.

## How it works

A scheduled job downloads and validates Fimea's shortage file and saves a dated snapshot when its contents change. The site joins package records to the current basic register by VNR and builds a static site. It can be searched by medicine, strength, substance, ATC, company or VNR; it includes veterinary products. Earlier copies from the Internet Archive extend the timeline. The download links on the site provide the current dataset.

The archive checks Fimea four times daily at 04:35, 10:05, 15:35 and 21:05 UTC to reduce the chance of a missed day. A separate Pages build runs daily at 04:55 UTC as a safety net. When a scheduled or manual workflow starts more than 30 hours after the last successful archive check, it raises a data-pipeline issue until an archive check succeeds. If GitHub starts no workflows at all, that alert will be late; the site itself shows a stale-data warning after more than three days.

**Source freshness.** The home page shows, next to the headline, "Fimea file last modified: <date>" (the HTTP `Last-Modified` of `Shortages.txt`, the file modification time, not a release time) and "Checked by Shortage Radar: <date>" (the last successful archive job). The `Last-Modified` is saved in `data/source/metadata.json` whenever it differs from the stored one, also when the content is the same. A saved time is kept only while the bytes are the same: new bytes without the header are stored as unknown (`null`), never with the old file's time. A banner appears on every page when the Fimea file has not changed for more than 2 days, or the register's run date (`Ajopvm`) is older than 2 days (Helsinki days; Fimea has changed the file on weekends, so the limit is two days). The limit is `STALE_DAYS` in `scripts/source_age.py` and in `site/lib.js`, and a test keeps the two equal. The archive job also runs `scripts/source_age.py`; when a file is stale it opens or updates the `data-pipeline` issue (entry `source-stale`) and closes it when the files are fresh again. A date that is missing or unreadable counts as unknown, not stale.

**Register source.** `scripts/fetch_register.py` builds the file name from the year (`Perusrekisteri2026.xml`), not from a fixed name. It stops with a clear message, keeps the old register and (in the archive job) opens the `register-source` issue entry when the file of the next year exists (`NEXT_YEAR_EXISTS`: a person checks it and changes the source), when no register is found (`MISSING`; last year's file is accepted in January only while its run date is at most 2 days old), or when the file has no readable run date. The register's name, run date and file time go to `data/source/register-metadata.json` and the site's source credit.

The list page loads `current.json`. The other pages load small files built with it, so no page downloads the whole archive: `summary.json` (counts, impact counts, longest and newest packages) for home, trends and about, `p/NN.json` (every notice of the packages whose VNR ends in NN, and the other packages in the substitution groups of its current packages) for the medicine page, `history.json` for the trends page and `week.json` for the weekly facts. The search also reads Finnish substance names (`substance_fi` in `current.json` and `removed.json`, made by `finnish_pairs` and `search_names` in `scripts/build.py`; the register writes `Aine` in English only). A name is used only when the whole English substance name of a one-substance product pairs with the product's one-word ATC name ("Tadalafil" and `tadalafiili`), at least two products give the pair and all agree, and the Finnish name spells like a word of the English name. Nothing is inferred from a shared first word, and class names ("elektrolyytit") and unverified pairs are left out: no result is better than a wrong one. A name matches from its start or in a Finnish case form ("galantamiinia"); it finds packages and says nothing about supply. `removed.json` (one row for each package that was listed earlier and is not now, with the capture it was last seen in and its gaps; `scripts/removed.py`) is read only when a search finds nothing on the current list, so the list page can show "Earlier on the list: last seen <date> (capture)" with a link to the archived medicine page. A past listing never means that supply returned. `names.json` (every trade name with the strengths the register writes for it, written "Name|strength|strength", and every active substance name, once each; `name_index` in `scripts/build.py`) is read when the home page search runs. A typed label is exact when each word starts a word of a name or substance and the typed strength, if any, is exactly one the register has (same numbers, same units; "5 mg" is not "50 mg/g"). An exact name that is in the register but not on the lists gets the "Not on Fimea’s list now" card. A typed label that is not exact (a typing mistake, a word from the middle of another name, a strength the name does not have) gets "Did you mean" with near names to choose and no statement about the typed text, so a mistake never hides a shortage or reads as "not on the list". Only a name that is near nothing gets "We did not find this name in Fimea’s medicine register". If the file cannot be loaded, the shortage cards still show with a note that name search is limited, and the page never says that sentence. The downloadable `data.json` retains the complete event history. `week.json` holds the counts for the "This week" summary, and `feed.xml` (English) and `feed-fi.xml` (Finnish) are Atom feeds of the shortages that appeared or left the list in the last 14 days and of the substitution groups that newly have no interchangeable package found in the data, with at most 200 entries.

### Impact: interchangeable packages in the data

For each current shortage, the build counts the other packages in the same substitution group (vaihtokelpoisuusryhmä) whose register entries say they are on the market and not in shortage, excluding packages listed in the current shortage file. Only Fimea's group code is compared. The register writes the strength and form of one group in different ways ("20 mg/ml" and "20 mg/g", film-coated tablets and capsules), and an earlier version that also compared that text found no alternative for 30 packages that had one. This is not a pharmacy stock check, and a group does not establish that a particular package is suitable.

**One rule for an available alternative.** `is_available_alternative` in `scripts/triage.py` is the only definition. It is used for the impact levels, the list of other packages on the medicine page and the history of newly critical groups, and a test checks that the three agree on the same register. A package of the same group is an alternative when it is not in the shortage file (VNR or old VNR), is on the market by its market entry and exit dates, and, on the register's own day, the register's flags agree (`Kaupan` is 1 and `Saatavuushairio` is 0; an empty flag does not count). The register has no earlier flags, so the history uses them only for the capture dated the same day as the register's `Ajopvm` (`register_date` is passed to `newly_critical`), and reads the market dates for every other capture; a package with no entry date has no dates, so today's market flag decides for it (`on_market`). That is the one difference between the current view and the history. It is also written on the About and Trends pages. On 23 Nov 2026 nine packages had an entry date and no exit date while the flag said they were not on the market; the flag wins for today.

Each current shortage gets one impact level (`impact` in `current.json`, `data.json` and the CSV; counts in `summary.json` under `impact`), set in `scripts/triage.py`:

| Level | Meaning |
| --- | --- |
| `substitute` | Interchangeable package found in the data: the group has at least one other package that meets the check: the register marks it as on the market and not short (`Kaupan` 1, `Saatavuushairio` 0), and it is not on the shortage list. |
| `no_alternative` | No interchangeable package found in the data: the package has a group, but no other package meets the check. This is not a statement that no treatment exists. |
| `nogroup` | No substitution group: the pharmacy cannot change the medicine on its own. |
| `vet` | Veterinary medicine (ATC starting with Q). Substitution groups are for human medicines, so these are counted apart from the human headline. |

On 22 Nov 2026 the split was 531 / 60 / 119 human packages and 39 veterinary packages, 749 in all. The home page shows the three human levels, each linking to the list filtered by it (`shortages.html?impact=no_alternative`). With `impact=no_alternative` the list shows one row per active substance and form, which opens to its packages. The medicine page names the other packages of the group with strength, pack and company, so the label can be checked.

The CSV column `other packages on market` gives the count, or is empty when no substitution group is recorded; `substitution group` gives Fimea's group code and `impact` the level. `impact` is Shortage Radar's own reading of Fimea's files, not a Fimea field; the source credit in the CSV and JSON says so. The CSV uses UTF-8 with a BOM and contains package, medicine, company, date and veterinary fields.

**Change: `critical` is now `no_alternative`.** The impact level that was called `critical` is called `no_alternative`, in the `impact` address parameter (`shortages.html?impact=no_alternative`), the `impact` field of `current.json`, `data.json` and `p/NN.json`, the `impact` column of the CSV, the `impact` counts of `summary.json` and the rows of `data/triage-counts.json`. The old name is an alias for one release: the address `?impact=critical` still opens the same list (the address is written with the new name as soon as a filter changes or the link is copied), the counts in `summary.json` and `data/triage-counts.json` carry `critical` next to `no_alternative` with the same value, and the site reads the old name in files saved earlier. The `impact` value of each package in the JSON files and the CSV has only the new name. After that release the alias and the old count keys are removed (`ALIASES` in `scripts/triage.py`, `IMPACT_ALIASES` in `site/lib.js`). The meaning of the level is the same. This is not the EU Union list of critical medicines (below): the `critical.*` pages, files and the EU list wording keep their names.

"Newly critical" is the first capture in which the captures show a substitution group with no other package that meets the check. In the history a package did not qualify when it was on that capture's shortage list or its market end date had passed; the register's own market and shortage flags count only for the capture dated the same day as the register. The register describes only today, so the history is rebuilt from the saved captures with today's group membership and the market entry and exit dates the register gives for each package. A group changes state only when the new state holds in two captures in a row, each at most 14 days apart, and no change is dated across a longer gap. On the archive up to 22 Nov 2026 this finds 20 events since 15 Sep 2026; each one is explained by its last alternative appearing on the shortage list or, once, leaving the market. Group changes and packages withdrawn from the register cannot be seen, so older events are less certain. To keep a record that does not depend on a later register, the archive job also downloads the register and saves the day's impact counts in `data/triage-counts.json` (`scripts/record_triage.py`); a failure there does not stop the archive. The JSON records the UTC build time as `generated_at` and the most recent successful archive check date as `last_checked`, which can be empty. When that date is unavailable, the site labels the build-time fallback and does not imply that the source was checked at build time.

**Daily ledger.** The daily job also appends one row per package on the list to `data/ledger/YYYY-MM.jsonl` (`scripts/ledger.py`), one file for each month. A row has `date`, `vnr`, `group` (substitution group, empty when none), `impact`, `alternatives` (other packages in the group on the market and not short; null without a group), `register_date`, and the SHA-256 of the two source files (`shortages_sha256`, `register_sha256`). Rows are only added, so rows written before the rename of `critical` to `no_alternative` keep `critical` in `impact`; read the two names as the same level. The first run of a day writes that day's rows and later runs on the same day add nothing, even if the source changed in between. A date with no rows was not recorded.

**Register date of a ledger day.** The ledger takes the register the job downloaded just before it. Fimea publishes the register of a day at about 00:30 UTC (02:30 Helsinki), and a scheduled run can start late. The rows of 25 Nov 2026 were written by a run at 00:04 UTC, before the register of 25 Nov existed, so they carry `register_date` 2026-11-24. The order of the steps is right (the register is fetched before the ledger); the first run of the day is the only one that writes, so the rows keep the older register. This is why `register_date` is in every row, and why check 6 below warns when it is older than `STALE_DAYS`. Impact counts did not change on that day (63 both ways); `alternatives` differs in 5 rows from a recomputation with the later register.

**Daily checks.** `scripts/validate_daily.py` runs in the archive job right after the ledger step and before anything is committed or published. It only reads: a failed check deletes and changes nothing. It prints one line for each check in the run log. A FAIL opens or updates the entry `data-validation` of the `data-pipeline` issue (`scripts/pipeline_alert.py`, the same issue as `source-stale`) and passing checks close it; a WARN is only written to the log. Checks: (1) every ledger VNR joins to the register by VNR or old VNR, FAIL; (2) `alternatives` is the same for all packages of a group and is null exactly when the group is empty, FAIL; (3) no (date, vnr) twice in the month file, FAIL; (4) the row count is within 10% of the previous recorded day, WARN; (5) `alternatives` is not more than the number of other packages of the group in the register, FAIL; (6) the rows' `register_date` equals the ledger date or is at most `STALE_DAYS` old, WARN when older; (7) the ledger VNR set equals the VNR set of the snapshot and `shortages_sha256` is the snapshot's hash (after a same-day refetch the superseded file the rows were made from also counts), FAIL; (8) `impact` is `substitute`, `no_alternative`, `nogroup` or `vet`, and `critical` only in rows dated up to 24 Nov 2026, FAIL. A day with no rows is also a FAIL. Checks 1 and 5 compare with the register file; they are skipped, and the log says so, when a later run of the day downloaded a different register from the one the rows were made with. A skipped check is not a pass: the alert can close on the other checks although checks 1 and 5 were not run again.

**Reading old impact values.** Every query over the ledger history reads it with `ledger.read_rows`, which passes `impact` through `triage.canonical_impact`: the old `critical` reads as `no_alternative`. Rows are never rewritten, so a query that reads the files directly must call `canonical_impact` itself.

**Daily counts (denominators).** The register has no history, so how many packages a company or a group had on an earlier day cannot be found later. `scripts/counts.py` saves it from 25 Nov 2026: `data/ledger/counts-YYYY-MM.jsonl`, one file for each month, rows only added. The first run of a day writes that day; later runs on the same day add nothing; a missing day was not recorded (the same rule as the ledger). The rows of a day are made from the shortage file and the register that the ledger rows of that day were made from (their SHA-256): when the register on disk is another one, the run writes nothing and the log says so, so counts and ledger rows of one day always agree. A day is added in one atomic step; an incomplete last line left by an older interrupted write is removed on the next run, with the rows of that day, which are then written again, and the archive job does not commit a counts file that does not parse. The 25 Nov 2026 rows were written by hand, the day this was added, from that day's snapshot and the register of 24 Nov (run date 2026-11-24, the register the ledger rows of 25 Nov used); no earlier day is filled in. A row has `type` `company` or `group`. A `company` row is one register holder with at least one package on the shortage list: `listed` (reported shortages, one for each VNR), `on_market` (register packages with `Kaupan` 1), each split into `_human` and `_vet` (ATC starting with Q), and `register_date`. A `group` row is one substitution group with at least one listed package: `on_market` (packages of the group that `triage.on_market` accepts on that day), `listed`, `alternatives` (packages that `triage.is_available_alternative` accepts, the same number the ledger writes for the group: interchangeable packages found in the data), `distinct_alternative_holders` (distinct register holders among them) and `register_date`. Companies come first, by name, then groups, by code. A holder with no listed package has no row. These are counts of packages, not of sales or stock. One day is about 87 KB (525 rows on 25 Nov 2026), so about 32 MB a year before compression; a day compresses to about 5 KB.

**Same-day refetch.** When a later run of the same day finds that the shortage file changed, the run does not fail and later steps still run. The day's snapshot becomes the newer content, so the site shows the latest file, and the replaced content is kept in `data/snapshots/superseded/<day>T<HHMMSS>Z-<hash>.txt` (UTC time of the run that found the change and a hash of the replaced bytes, so no version is overwritten); the run log says so. The SHA-256 in the day's ledger rows matches the superseded file when the ledger was written before the change. A failure in this step does not stop the archive.

The history shows saved captures, not daily observations. Capture gaps can be long: the first is from 18 November 2024, followed by a gap until September 2026. The chart does not interpolate across long gaps.

**Gaps are unknown time, not presence.** Two consecutive captures more than 14 days apart (`MAX_GAP_DAYS` in `scripts/gaps.py`, the one place where the limit is set; exactly 14 days is still joined) tell nothing about the days between them. A notice listed on both sides of such a gap was not observed in between, so it is not shown as listed throughout: the medicine page says "Not observed between 18 Nov 2024 and 15 Sep 2026." instead. In `data.json`, `current.json` and `p/NN.json` every event keeps `first_seen` and `last_seen` (the first and last capture that listed it, gaps included, as before) and has three new fields: `spans`, the runs of captures without a long gap (`[{"first_seen", "last_seen"}]`), `gaps`, the stretches not observed (`[{"from", "to", "days"}]`, from the last capture before to the first capture after), and `removed_after_gap`, true when the capture that no longer lists the event is more than 14 days after the last one that did, so the removal date is unknown. The feeds add a "Not observed between" line to an entry with a gap. The EU list history pages and alert feeds already used the same limit. An event is identified by VNR, reported start, notification date and company; changes to those fields can appear as a removal and a new event.

**End dates that changed.** The Trends page gives one dated fact: how many of the notices on the list now changed their estimated end date in our captures (`end_changes` in `history.json`: `current`, `changed`, `from`, `to`, `max_gap_days`; `end_date_changes` in `scripts/build.py`). A change counts only when the capture that first shows the new date is at most 14 days (`MAX_GAP_DAYS`) after the capture before it; across a longer gap the date may have changed at any time, so that change is not counted. A notice counts once, however many times its date changed, and one that left the list is not counted. A change before the first capture, or one made and undone between two captures, is not seen. The dates are the companies' reports; the count says nothing about whether supply returned. The page no longer shows a share of shortages that stayed listed past their estimate, its bars, or a ranking of companies (the `delays` key of `history.json` and `data.json` is gone).

## Pages and structure

The site is static and has five pages, all under `/shortage-radar/` on GitHub Pages. Text is in Finnish and English; the language follows the browser and the choice is remembered on the device.

| Page | File | What it does |
| --- | --- | --- |
| Home (Etusivu) | `index.html` | One sentence on today's situation, with when Fimea's file changed and when Shortage Radar checked it ("Fimea: N short now, M more expected within 2 weeks."), the impact triage (interchangeable package found in the data, none found in the data, no substitution group), a search, the newest packages, three facts from this week and three paths. The old `?q=` address is sent to the list. |
| Shortages (Saatavuushäiriöt) | `shortages.html` | The full list with search, filters (impact, status, medicine group, form, company) and sort. The search and filters are in the address, for example `shortages.html?q=burana&status=now` or `shortages.html?impact=critical`, which groups the packages by medicine. |
| Medicine (Lääke) | `medicine.html?vnr=<VNR>` | One package: label, whether the check found an interchangeable package and the other packages of its group, status, timeline, what to do, details and a link to share. Feed entries link here. |
| Trends (Tilastot) | `trends.html` | Count over time, this week, groups, earliest reported starts, groups newly without an interchangeable package in the data, the recorded impact counts, the end dates that changed and a citation. |
| About (Tietoa) | `about.html` | What a shortage is, what to do, substitution groups, what the impact label means and its limits, how the data works, limits, downloads, privacy and licence. |

The pages are built by `scripts/pages.py`, which writes the shared header and footer once into every page, and `scripts/build.py` runs it with the data. The generated pages are not committed. Browser code is in `site/`: `i18n.js` holds all text, `lib.js` the shared code (search, dates, the package card, filters, the timeline model, page set-up) and one script for each page. Form pictograms are drawn in `lib.js`. The font is Atkinson Hyperlegible Next, hosted in `site/fonts`; its digits are replaced by Public Sans digits (a 3 KB subset under the same family name) because Atkinson's zero is slashed and reads as a letter in dates and doses.

## Critical medicines in Finland

`critical.html` (nav label "EU list") shows which packages on Fimea's shortage list are on the EU [Union list of critical medicines](https://www.ema.europa.eu/en/human-regulatory-overview/post-authorisation/medicine-shortages-and-availability-issues/union-list-critical-medicines), pinned at version 2.1 (EMA/229885/2026, 4 Nov 2026) in `data/critical/eu-list.csv` with the source row of each entry. A package is an `exact` match when its ATC level 5 code is on the list, the list substance is among its active ingredients (`data/critical/ingredients.json` holds the names the register spells differently) and one of its routes (Fimea `Antoreitti`) fits a list route. It is `route-mismatch` when code and ingredient match but the route does not (or Fimea gives no route: "route unclear"), `ingredient-mismatch` when the code matches but the ingredient is not confirmed, and `unmatched` when the VNR is not in the register. Ongoing (Voimassa K) and not yet started (E) notices are counted apart. In the history a notice that was edited, or that vanished from some captures and came back, is one shortage; a gap in the captures is unknown time and the length is given as days between captures. Fimea's `EUKriittinenValmiste` flag is only a cross-check, shown in the note. The route table is `data/critical/routes.json`; there are no keyword rules. Facts only: no advice, score, forecast or alternatives.

The EU pages hold every text in English and Finnish (`scripts/critical_copy.py`, `critical_copy_methods.py`; the Finnish is a draft): both versions are in the HTML as `l-en` / `l-fi` spans and the style sheet shows the one that matches `<html lang>`, so a language change needs no reload; `site/critical.js` swaps option labels, placeholders, aria-labels, SVG titles and the document title. `scripts/build.py` writes the match page, `critical-methods.html` (sources, licences, the rule, the hand-checked rows, limits), one page per code (`critical-<ATC>.html`: list row, Fimea notices, what the archive shows, with "last seen" for notices that left), the downloads `critical.csv` and `critical.json`, and the alert feeds `critical-feed.xml` (RSS) and `critical-feed.json` of new exact-match shortages of the last 30 days. The daily Pages build, which also runs after each archive check, produces the feeds. The register is now read from `Perusrekisteri2026.xml`, which carries the route and flag fields; the existing fields are unchanged. To update the list, run `python scripts/fetch_critical.py list` (it refuses a version other than the pinned one unless `--version` is given; it sends a User-Agent, pauses and caches); `python scripts/fetch_critical.py forms` refreshes the dosage form names. The EMA licence is its copyright notice (reuse with EMA acknowledged), not CC BY; Fimea data is CC BY 4.0.
